### 4.1 `GET /v1/health` 的 `vram_gb` 字段口径

**上表的采样值与端点返回的字段不是同一回事**，两者不能互相替代：

| | 说明 |
|---|---|
| 上表 | **开发实例上的实测记录**，用来说明权重与上下文占用确实远低于 32 GB |
| `vram_gb` 字段 | **运行时归因值**：把计数归到模型服务实际持有的那块卡 |
| 实测返回值 | **18.94 GB**（`renderD133` → `card6` → PCI `0000:a3:00.0`） |

**为什么必须归因，而不是直接读 GPU[0]**：本开发实例上有 **8 块 AMD GPU**，且**别的租户也占着其中几块**。
把所有卡相加会得到约 **67 GB**，远超 32 GB 上限——**这个数字与我们无关**，却会让就绪检查错误地失败。

**归因失败时返回 `null`，不回退到「最忙的那块卡」**：

- 共享主机上「最忙的卡」很可能是**别人的**，把它的数字当成我们的，比不给数字更糟；
- `null` 表示**没有测到**，**不等于已证明满足显存限制**；
- 就绪判定只对**实测值**做 32 GB 判断；测不到时视为**仪表缺失**，不因此报 `ready: false`
  （否则会因为我们的观测手段问题而自我拒绝）。

**决赛验收仍需在官方基础镜像与目标卡上重新实测**——`null` 或本节的开发实例数值都不能替代它。

**实测口径的重要说明**：上述显存值为**开发实例（gfx1100，47.98 GiB 卡）**上的运行时采样，**不是**决赛目标卡（记录为 W7900/gfx1100 与 R9700/gfx1201，按单卡 32 GB 设计）上的复测值。量化权重 19,095,766,304 字节本身即低于 32 GB 上限，但**最终显存占用必须在官方基础镜像与目标卡上重新实测**，不得以本值冒充实测验收结论。
