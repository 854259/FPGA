### 4.1 `GET /v1/health` 的 `vram_gb` 字段口径

当前提交源码为 PR262 的 `runtime411473e5`（源码提交 `1725537c`，合并 `16edef0b`）；它沿用无回退的显存归因函数。模型声明中的历史实验分数、health 采样和较早运行时版本，均不构成当前源码的真实模型/资源/部署资格。

**当前行为**：依据模型服务持有的 render 节点定位对应设备，读取设备 VRAM 计数；归因失败返回 `null`，不回退到最忙的卡。这里是所归属设备的计数，不是该进程独占显存的证明。字段名为 `vram_gb`，实现按字节除以 `1024 ** 3`（GiB）并保留三位小数；正式 32 GB 门槛及计量口径仍须随完整资源证据核验。

**历史版本记录**：`cea6479c` 在归因失败时返回最忙设备的值，可能属于别的租户；`728499f4` 修掉了这一回退。历史备份 `release/runtime.cea6479c.py` 的 SHA-256 为 `cea6479c6364fbfce55ca8129e8cfd7bb4b9afd3b2a4c7ae2e3cd381af2968b1`，仅作归档来源，不是当前回退/部署指令。`728499f4` 单轮全量 agent 0.7468 对比旧版 0.7667，未满足当时预登记采纳门槛；旧门槛仅描述该轮，不作为当前选优的额外否决门。baseline 的 21/156 翻转不能视为固定噪声率；缺少 `declaration_fix` 接受事件也不能证明补丁未执行。此前据此推断“补丁无害”的说法保持撤回，不把求解分数变化归因于未在求解路径调用的显存函数。历史版本依据仍为仓库 `05_handoff/RELEASE_20261003.md`。

**上表的采样值与端点返回的字段不是同一回事**，两者不能互相替代：

| | 说明 |
|---|---|
| 上表 | **开发实例上的历史采样记录**；不是加载、生成、修复全过程峰值或独占资源证明 |
| `vram_gb` 字段 | **运行时设备归因值**：定位模型服务持有的卡后读取该设备计数；不等同进程专属占用 |
| 历史端点返回值 | **18.94**（实现单位 GiB；`renderD133` → `card6` → PCI `0000:a3:00.0`），不是当前采样 |

**为什么必须归因，而不是直接读 GPU[0]**：本开发实例上有 **8 块 AMD GPU**，且**别的租户也占着其中几块**。
把所有卡相加会得到约 **67 GB**，远超 32 GB 上限——**这个数字与我们无关**，却会让就绪检查错误地失败。

**归因失败时返回 `null`，不回退到“最忙的那块卡”**（当前源码沿用的行为）：

- 共享主机上「最忙的卡」很可能是**别人的**，把它的数字当成我们的，比不给数字更糟；
- `null` 表示**没有测到**，**不等于已证明满足显存限制**；
- 非 `development` 配置下，就绪判定只对**实测值**做 32 GB 判断；测不到时视为**仪表缺失**，不因此报 `ready: false`
  （否则会因为我们的观测手段问题而自我拒绝）。

**决赛验收仍需在官方基础镜像与目标卡上重新实测**——`null` 或本节的开发实例数值都不能替代它。

**实测口径的重要说明**：上述显存值为**开发实例（gfx1100，47.98 GiB 卡）**上的运行时采样，**不是**决赛目标卡（记录为 W7900/gfx1100 与 R9700/gfx1201，按单卡 32 GB 设计）上的复测值。量化权重 19,095,766,304 字节本身即低于 32 GB 上限，但**最终显存占用必须在官方基础镜像与目标卡上重新实测**，不得以本值冒充实测验收结论。
