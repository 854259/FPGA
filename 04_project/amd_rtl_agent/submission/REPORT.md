# AMD 题目一 RTL track · 设计报告

- 更新时间：2026-10-02
- 队伍：45561
- 赛道：AMD 题目一「RTL/HLS 本地智能体设计赛道」的 **RTL track**
- 本报告的每一项数字都绑定可复现的运行证据；未核实项明确标为未发布或待实测，不估算、不冒充实测。

---

## 1. 目标与边界

方案是一个**本地、断网运行的 RTL 代码生成智能体**：输入题目文本，输出单个可综合的 `Verilog/SystemVerilog TopModule`。交付物是官方方案包结构（`agent/` 源码 + `skill/` 技能包 + `serve/` 推理服务 + 赛事方 `baseline.py` + `Dockerfile`/`MODEL.md`/`REPORT.md`）。

**边界**：

- 只做 RTL track，不做 HLS。
- 未做模型微调——直接用上游开源量化权重，避免抬高基线并简化开源合规。
- 赛事方官方基础镜像、隐藏题集、最终调用协议与时间预算**尚未发布**。当前所有结果都是 development profile 下的开发验证，**不是赛事方最终隔离镜像的验收结论**。
- 本方案的全部通过率结论均为**单样本 pass@1**，不是 pass@5；正式总分需赛前公布的增益满分线与代价基准时长。

## 2. 赛道要求与对应的设计决策

官方评测是**远程投题**而非提交容器：赛事方从外部调用队伍自己跑起来的服务。契约与判定口径固定在官方仓库 commit `afd135e7ba5f6ec4c6d77e7c927c894327537801`，按字节保存在 `official_reference/`。

| 官方要求 | 我们的实现 |
|---|---|
| `GET /v1/health` 返回 `track: "rtl"`，Bearer 鉴权 | `agent/runtime.py` 的 `serve` 子命令；仅绑 `127.0.0.1` |
| `POST /v1/solve`，`mode` 区分 `agent`/`baseline` | 同一端点、同一服务、同一模型，仅 `mode` 不同 |
| 单题墙钟上限由赛事方给，超时按 L0 且不重投 | 运行端按 `deadline_s` 自我限时；收到信号 10 s 内退出 |
| `run.sh <in> <out>` 读 `prompt.txt`、写 `solution.v` + `trace.jsonl` | 已实现；RTL 下 `interface.txt` 恒不提供 |
| L0–L3 递进判定（编译 0.2 / 仿真 0.7 / 综合 1.0，器件 `xczu3eg-sbva484-1-e`，5 ns） | 外部判定器 `official_eval.py` + 固定 `judge.py`，**参考解与测试台绝不进入模型上下文** |
| 计分用 pass@1 | 运行端按系数取平均 |
| 断网运行 | 模型与工具链全部本地，权重可离线加载 |
| 红线：不联网检索、不硬编码答案、不绕过模型 | 技能包只含通用规则，无题号/题解；模型对每题都有实质生成作用 |

## 3. 架构

```text
task/prompt.txt
  ├─ baseline 模式：题目原文 → 单次生成，不重试、不用工具、不加载技能
  └─ agent 模式：技能包 + 题目 → 生成 → xvlog 编译自检
                  └─ 失败时带上工具反馈再生成一次（最多 1 次修复）
      ↓
   solution.v + trace.jsonl
      ↓（由外部判定器，不在方案包内）
   judge.py → L0–L3 → score.py 汇总
```

实现刻意保持扁平：`agent/runtime.py` 单文件包含 HTTP 服务、限时子进程监督、提示装配、编译自检与 `trace.jsonl` 记录。没有框架、数据库、检索层或多智能体编排。

**关键隔离**：判定器与参考解位于方案包之外；`prompt.txt` 是模型唯一可见的题目信息。

## 4. 模型与推理栈

| 项 | 值 |
|---|---|
| 模型 | `ggml-org/Qwen3.6-27B-GGUF`，revision `8a7ee08e8b9bfb857107ecc25a5599d2f38b76f8` |
| 量化 | Q4_K_M（19,095,766,304 字节，SHA-256 `65b753ea…d1c49921`） |
| 许可 | Apache-2.0，本地开源权重，非商用 API |
| 后端 | `llama.cpp` `llama-server` v0.5.0-dev c13fcbf（HIP，gfx1100） |
| 上下文 / 输出上限 / 温度 | 16,384 / 8,192 / 0 |
| 思考开关 | `--reasoning off`（实测生成不含 `<think>` 残留） |
| 单卡显存 | 实测约 **19.0 GiB**（`20,376,678,400` 字节，gfx1100 开发卡），低于 32 GB 上限 |

详细声明见 `model/MODEL.md`。

**思考开关是一项实测发现，不是默认选项。** Qwen 系模板在未显式关闭思考时会输出 `<think>` 块；运行端不发送 `enable_thinking`，开关完全由服务端参数决定。2026-09-27 在未关闭思考的配置下实测 agent 调用截断率 **37.1%**（79/213）；关闭后降到 **1.8%**（3/167）。若不处理，输出会被思考 token 吃掉而截断，并被误读成模型能力问题。

### 4.1 模型选择依据（做过对照，不是拍脑袋）

我们实际比较过两个基座，用**同配置单变量**方式跑满 156 题：

| | Qwen3.6-27B | iCoder-27B（RTL 专精微调） |
|---|---:|---:|
| agent 题集得分 | 0.7603 | 0.7679 |
| **baseline 题集得分** | 0.6590 | **0.7564** |
| 能力分 | 22.81 | **23.04** |
| **增益倍数** | **1.127** | 1.015 |
| 能力 + 增益 | **28.04** | 23.69 |

iCoder 的**裸模型更强**（基线高 0.097，编译失败 10 次 vs 我们 22 次），但赛事把 40 分押在「相对自己裸跑基线的增益」上。基线太高，agent 加不动，增益趋近 1，增益分几乎归零——**更强的模型反而总分更低**。

结论：保留 Qwen3.6-27B。这条判据也写进了我们的经验：选基座要同时看裸基线高度和 agent 可提升空间。

## 5. 控制流与验证

- **baseline**：恰好一次模型调用，单条 user 消息，无技能、无重试、无工具。这是官方基线契约，我们不做任何改动（`baseline.py` 与 `run_baseline.sh` 按字节固定并在运行前校验 SHA-256，不符则 `baseline_integrity()` 直接拒绝运行）。
- **agent**：加载技能包 → 生成 → `xvlog` 编译自检 → 编译通过即返回；失败则带反馈再生成一次。
- **反馈内容**：仅工具日志中的错误行，截断到上限，不含参考解、测试台或期望输出。
- **限时**：单题按 `deadline_s` 自我限时，超时杀整个进程树并返回已有候选。
- **可追溯**：每次模型调用与工具调用写入 `trace.jsonl`（含 token 计数与 `finish_reason`）。

## 7. 评测结果（官方 L0–L3）

全部在 AMD ROCm（gfx1100）+ Linux Vivado 2026.1 + llama.cpp HIP 上完成，代码 `a53e343`、数据 `c498220`、判定 `afd135e7` 固定。

| 阶段 | 结果 |
|---|---|
| 官方参考自检（156 题，不调模型） | **152/156 L3**，set_score 0.9782，零工具错误 |
| 全量配对（156 题 × 2 模式，312 样本） | **agent 0.7603**、baseline 0.6744，`complete=true`，零工具错误 |

分级明细：agent L3 111 / L1 38 / L0 7；baseline L3 98 / L1 36 / L0 22。

参考自检中非 L3 的 4 题（`Prob082` `Prob099` `Prob141` `Prob156`）在**两轮独立的 AMD 与 NVIDIA 运行中完全一致**，支持「上游数据集题面/参考不一致」而非本地环境问题；分母保留 156，不做剔除。

**能力分 22.81/30，增益 1.127**（增益得分需赛前公布的满分线倍数，本地不给正式值）。

## 8. 失败分析

这是本报告的重点。以下分析基于 **312 个样本的完整逐题判定与 `trace.jsonl`**，可复现。

### 8.1 失败集中在仿真，不在编译

| 模式 | L3 | 编译失败 | 仿真失败 | 综合失败 |
|---|---:|---:|---:|---:|
| agent | 111 | 7 | 38 | 0 |
| baseline | 98 | 22 | 36 | 0 |

**编译失败与仿真失败的比例约 1:5。** 这决定了优化方向：继续加固编译修复的边际收益已经很小，真正的失分大头是**功能正确性**。

值得注意的是 agent 的机制（编译自检 + 声明修复）在两种模式上的差别：它把 baseline 的 22 次编译失败压到 7 次，但仿真失败几乎没变（36 → 38）。

### 8.2 仿真失败的错配率分层

按官方判定器给出的 `mismatches / samples` 分布：

| 错配率 | 题数 | 含义 |
|---|---:|---|
| < 10%（近乎正确） | 8 | 只差一个边界条件 |
| 10–50%（部分错） | 17 | 逻辑大体正确，有具体缺陷 |
| 50–90%（大部分错） | 7 | 理解偏差较大 |
| > 90%（几乎全错） | 6 | 基本没写对 |

**25/38（66%）的失败错配率低于 50%**——这些是「大体正确但某个点错了」的实现。典型如 `Prob104_mt2015_muxdff` 1/199、`Prob053_m2014_q4d` 1/100、`Prob034_dff8` 1/41。

### 8.3 模型无关的失效模式（最有价值的发现）

我们比较了 **Qwen3.6-27B 与 iCoder-27B 两个完全不同的基座**，发现 **4 道题在两者上都回归**——即裸模型能通过、加上技能提示后反而失败：

| 题目 | Qwen 基线→agent | iCoder 基线→agent | 失效模式 |
|---|---|---|---|
| `Prob094_gatesv` | 1.00 → 0.20 | 1.00 → 0.20 | 向量边界下标理解错位 |
| `Prob143_fsm_onehot` | 1.00 → 0.20 | 1.00 → 0.20 | 输出逻辑漏掉一个状态 |
| `Prob150_review2015_fsmonehot` | 1.00 → 0.20 | 1.00 → 0.20 | 下一状态漏掉自环 |
| `Prob154_fsm_ps2data` | 1.00 → 0.20 | 0.20 → 0.00 | 数据通路未覆盖绕过中间状态的转移 |

**与模型无关，因此归因于提示而非模型。** 进一步观察这 4 题失败输出的共同特征：**长篇逐项枚举 + 推导注释**——模型把状态机/向量逻辑一项项列出来写，中途漏项。

这正是 7 规则版删掉「逐项核对」类规则后，`Prob094` 与 `Prob143` 被修复的原因。剩余 `Prob150`/`Prob154` 属于更难的两类遗漏，列为下一轮目标。

### 8.4 本底噪声：单题差异不构成结论

`baseline` 不加载技能包，其成绩**本应逐题不变**。但实测有 **5/156 题（3.2%）发生翻转**（`Prob086` `Prob100` `Prob103` `Prob133` `Prob140`）。

原因判断：`llama-server -t 8` 多线程下浮点归约顺序不固定，temperature 0 仍有约 3% 的单题翻转率。

**后果与自律**：单题 ±1 的变化不作为结论；本报告所有判读都建立在「净增题数 / 增益变化 / 配对净数」这类量级上。严格归因需多 seed 或 5 样本协议——这是我们下一步要补的方法学短板。

### 8.5 其它已定位的问题与处理

| 问题 | 处理 |
|---|---|
| 输出因思考块被截断 | 服务端 `--reasoning off`，截断率 37.1% → 1.8% |
| 编译错误 `VRFC 10-1280`（过程块赋值未声明为 reg） | 编译自检 + 简单 ANSI 输出声明自动修正，占修复次数且仍需完整 EDA 复验 |
| 修复把近似正确解改坏 | 按验证阶段与归一化错配率选择较好候选，退步时回退 |
| RTL 下 `interface.txt` 恒为空 | 接口信息只从题面读取，不依赖不存在的文件 |
| 包结构改动导致基线模块导入失败 | 由实跑验证发现（`ModuleNotFoundError`），已修正并加包根路径探测 |

## 9. 尚未验证、不声称完成的项

- **官方基础镜像**：尚未发布；当前 `Dockerfile` 是开发版，未按官方镜像重建，也未验证可独立重建。**这一项未满足会导致全部运行类得分无法产生，是当前最大的外部风险。**
- **最终目标卡显存实测**：现有 19.0 GiB 采样来自 gfx1100 开发卡，不是决赛卡（记录为 W7900/gfx1200 系列，按单卡 32 GB 设计）。
- **官方时间预算与增益满分线**：未公布，因此「代价分」与「增益得分」无法给出正式值。
- **pass@5**：未运行，现有结论均为单样本。
- **ROCm 后端与官方镜像的最终组合**：仅验证了开发实例上的 HIP 构建。

## 10. 复现

方案包内（`submission/`）：

```bash
# 1. 启动推理服务（先设置 MODEL_PATH 指向量化权重）
MODEL_PATH=/opt/models/Qwen3.6-27B-Q4_K_M.gguf ./serve/llama.sh

# 2. 单题运行
./run.sh  /path/to/task /tmp/agent-out
./run_baseline.sh /path/to/task /tmp/baseline-out

# 3. HTTP 服务
python3 agent/runtime.py serve --port 7860
```

评测（判定器在方案包之外）：

```bash
export XILINX_VIVADO=/tools/Xilinx/2026.1/Vivado LLM_BASE_URL=http://127.0.0.1:8000/v1
export MODEL_NAME=Qwen3.6-27B-Q4_K_M RTL_PROFILE=development
python3 official_eval.py --tasks <题目目录> --out <新目录> --samples 1 --deadline 300
```

离线复盘：`bench/analyze_official_run.py`。
