## 1. 目标与边界

方案是一个**本地、断网运行的 RTL 代码生成智能体**：输入题目文本，输出单个可综合的 `Verilog/SystemVerilog TopModule`。交付物是官方方案包结构（`agent/` 源码 + `skill/` 技能包 + `serve/` 推理服务 + 赛事方 `baseline.py` + `Dockerfile`/`MODEL.md`/`REPORT.md`）。

**边界**：

- 只做 RTL track，不做 HLS。
- 当前采用上游开源量化权重，未做模型微调。模型选择以官方总体得分和部署条件为依据，同一选择公平应用于原样官方基线。
- 调用协议已在锁定官方版本的 `docs/API_CONTRACT.md` 发布；基础镜像具体版本、隐藏题集与最终时限公告尚未在本地核验。现有结果属于开发验证，**不是赛事方最终隔离镜像的验收结论**。
- 历史章节包含单样本结果，第 8.7 节已完成每题五样本。各项结果列明样本量，L0–L3 加权题集得分与 L3 完全通过率分开记录，不跨轮拼分。

## 2. 赛道要求与对应的设计决策

官方接口采用**外部投题到队伍服务**；同一锁定版本的 README/SCORING 仍列有源码、Dockerfile、模型声明和报告等提交物。远程接口不构成省略交付要求的依据，最终部署方式按赛前公告核对。契约与判定口径固定在官方仓库 commit `afd135e7ba5f6ec4c6d77e7c927c894327537801`，按字节保存在 `official_reference/`。

| 官方要求 | 我们的实现 |
|---|---|
| `GET /v1/health` 返回 `track: "rtl"`，Bearer 鉴权 | `agent/runtime.py` 的 `serve` 子命令；仅绑 `127.0.0.1` |
| `POST /v1/solve`，`mode` 区分 `agent`/`baseline` | 同一端点、同一服务、同一模型，仅 `mode` 不同 |

## 3. 归档提交包架构（新研究候选见 8.7）

```text
task/prompt.txt
  ├─ baseline 模式：题目原文 → 单次生成，不重试、不用工具、不加载技能
  └─ agent 模式：技能包 + 题目 → 生成 → xvlog 编译自检
                  └─ 失败时带上工具反馈再生成一次（最多 1 次修复）
      ↓
   solution.v + trace.jsonl
      ↓（由外部判定器，不在方案包内）
   judge.py → L0–L3 → score.py 汇总
```

实现刻意保持扁平：`agent/runtime.py` 单文件包含 HTTP 服务、限时子进程监督、提示装配、编译自检与 `trace.jsonl` 记录。没有框架、数据库、检索层或多智能体编排。

**关键隔离**：判定器与参考解位于方案包之外；`prompt.txt` 是模型唯一可见的题目信息。

## 5. 控制流与验证

- **baseline**：恰好一次模型调用，单条 user 消息，无技能、无重试、无工具。这是官方基线契约，我们不做任何改动（`baseline.py` 与 `run_baseline.sh` 按字节固定并在运行前校验 SHA-256，不符则 `baseline_integrity()` 直接拒绝运行）。
- **agent**：加载技能包 → 生成 → **三项检查** → 编译通过即返回；失败则带反馈再生成一次。
- **三项检查，按执行顺序**：
  1. **源码形态**：必须含完整 `TopModule` 且以 `endmodule` 结束；拒绝 `` `include `` 与文件 IO。
  2. **未定义子模块（纯文本，零工具成本）**：层次化设计实例化了未定义的子模块时，`xvlog` **不会报错**——分析阶段不解析实例化，只有判定器的细化阶段才失败。于是 agent 会交出一个自认为正确的设计而判 L0。本检查找出所有**带具名端口映射**（`.port(sig)`）的实例化，检查模块是否在同文件定义。
  3. **`xvlog` 编译**：唯一调用编译器的工具。
- **确定性声明修复（不花模型调用）**：编译报 `VRFC 10-1280`（过程块赋值给非 reg）或 `VRFC 10-9336`（ANSI 端口重复声明）时，用文本变换修：端口改 `output reg`，删除函数体里的重复 `reg` 声明。**只有重新编译通过才被接受**，否则回退到原来的模型修复路径。重新编译通过只证明该检查出口成功，不保证功能正确、总分更高或墙钟更短，仍须外部判定。
- **反馈内容**：仅工具日志中的错误行与上述文本检查的结论，截断到上限，**不含参考解、测试台或期望输出**。
- **限时**：单题按 `deadline_s` 自我限时，超时杀整个进程树并返回已有候选。
- **可追溯**：每次模型调用与工具调用写入 `trace.jsonl`（含 token 计数与 `finish_reason`）。新增事件：`check_submodules`、`declaration_fix`。

### 5.1 为什么"未定义子模块"要专门检查

这是本次工程改进中最有代表性的一处：**编译通过不等于设计正确，而这条鸿沟没有反馈可依**。

| | |
|---|---|
| 现象 | agent 交出的设计 `xvlog` 通过，判定器细化失败，判 L0 |
| 后果 | agent 认为成功，无从修正 |
| 常规解法 | 跑 `xelab`（细化），成本 **1.12 秒/题**，每题都付 |
| 我们的解法 | 纯文本判断，**成本约 0** |
| 验证 | 200 个真实生成解**零误报**，4/4 覆盖该类错误 |
| 实测收益 | 触发的 4 道 RTLLM 题里救回 1 道（`barrel_shifter` L0 → L3） |
| 主基准成本 | VerilogEval 156 题上**触发 0 次 = 0 秒** |

**关键是判据的选择。** 第一版写成"匹配任何 `Name inst (`"，在 VerilogEval 上误报 **69/156**——因为 `for (i = 0; ...)` 的循环变量被当成了模块名。改成**要求具名端口映射**后才降到零误报。

**这个错误是靠拿 `xelab` 实测结果做对照才发现的。** 没有对照，我们会推荐一个 44% 误报率的检查。

### 5.2 确定性声明修复的实测

`Prob058_alwaysblock2` 的候选把 ANSI 端口声明成隐式 wire，又在函数体里重复声明 `reg`：

```verilog
output out_always_comb,     // 隐式 wire
...
reg out_always_comb;        // 重复声明 -> VRFC 10-9336
always_comb begin
    out_always_comb = a ^ b;  // 赋值给非 reg -> VRFC 10-1280
```

| | 旧路径 | 新路径 |
|---|---|---|
| 模型调用 | 2 次 | **1 次**（与正常生成相同） |
| 结果 | **L0** | **L3** |
| 耗时 | — | **7 秒** |

**这个改动是"免费"的：只在编译已失败时多跑一次编译。**

### 5.3 HTTP 接口的契约合规（逐条实测）

赛前我们犯过一个值得记下的错误：**所有自检都走 CLI（`run.sh`），而赛事方走 HTTP**。
两者是不同的入口，因此契约里定义的要求，我们只验了自己习惯走的那条路。

**这个疏忽差点是致命的**：`GET /v1/health` 当时**恒报 `ready: false`**，而契约写明
*"赛事方在投题前调用，确认服务与模型就绪"*。两个独立根因：

| # | 根因 | 修法 |
|---|---|---|
| 1 | `vivado -version` 输出 `vivado v2026.1`（**小写**），正则找的是 `Vivado`，**永远匹配不上** | 加 `re.I`，超时由 5 秒放宽到 30 秒 |
| 2 | `vram_gb()` 把机器上**8 块 AMD GPU 的占用全加了**（含别的租户），报 67.4 GB，超过 32 GB 限制 | 归因到模型服务实际持有的那块卡（`renderD133` → `card6` → **18.94 GB**） |

**修完之后逐条实测：**

| 契约要求 | 实测 |
|---|---|
| `GET /v1/health` → `ready: true` | ✅ 两个 profile 均为 true |
| `track` 必须为 `"rtl"` | ✅ |
| `vram_gb` 为当前实测显存占用 | ✅ **18.94 GB**（与 `MODEL.md` 记录的 ~19.0 GiB 吻合） |
| 两个端点都校验 Bearer | ✅ 无 token → **401** |
| `POST /v1/solve` 响应字段 | ✅ **恰好** `task_id`/`solution`/`trace`/`elapsed_s` 四个 |
| `task_id` 原样带回 | ✅ |
| `interface` 为空串（评测实况） | ✅ 正常出解 |
| **失败时返回空字符串而非报错** | ✅ `deadline_s=1` → HTTP 200 + `solution: ""` |
| 缺 `task_id` / 非法 JSON | ✅ 均 **400** |
| **SIGTERM 后 10 秒内退出** | ✅ **0.10 秒**（在 EDA 工具运行中中断也一样） |
| 只绑 `127.0.0.1` | ✅ 代码为 `('127.0.0.1', port)` |

**`/v1/solve` 共 8 个用例，全部通过。**

#### 一处无害但已记录的观察

SIGTERM 打断时，worker 被 `SIGKILL`，其 EDA 孙进程成为孤儿并重新挂到 PID 1；
**本机的 PID 1 是 `jupyter-lab`，不承担回收职责**，因此僵尸进程会累积。

**量化后判定为无害**：单次中断约 2 个僵尸，5 样本协议全量约 3000 个，
而容器 `pids.max` 为 618610（占 0.5%）。**正常完成的样本不产生僵尸。** 记录在案，不做改动。

#### 这条教训已写进流程

**契约里定义了哪些接口，就要端到端验证哪些接口**——不能只测自己习惯的入口。
此后又有两次同类失误（`pkill` 包装脚本未杀子进程、`git checkout` 还原未跟踪路径），
共同点都是**验证了"我以为的机制"而不是"实际的结果"**。
现在的纪律是：任何"停止/还原/切换"之后，**直接核对最终状态**（进程没了、哈希对了、端口空了）。
