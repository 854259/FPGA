## 1. 单变量 A/B：针对性提示无效

### 做法

5 道已知「`xvlog` 通过、`xelab` 失败」的题，**只改一处**——细化失败时反馈里有无那句针对性提示：

| 变体 | runtime | 内容 |
|---|---|---|
| X | `3814e1dfac619511` | 有 `xelab`，反馈为原始错误 |
| Y | `daee060e7d814a5a` | 有 `xelab` **+** 「你实例化了未定义的子模块，请定义它或改为扁平实现」 |

温度 0，其余参数与基线一致。脚本 `directionA_ab.py`，先占 `slot.sh` 再跑，`finally` 还原 runtime。

### 结果

```
X_no_hint  首轮细化失败 4/5   修复后成功 2/5   模型调用 10   总耗时 503s
Y_hint     首轮细化失败 4/5   修复后成功 1/5   模型调用 10   总耗时 578s
```

| 题目 | X | Y |
|---|---|---|
| `adder_16bit` | [1,1] ❌ | [1] ❌ |
| `adder_32bit` | [1,1] ❌ | [1,1] ❌ |
| `barrel_shifter` | [1,0] ✅ | [1,0] ✅ |
| **`div_16bit`** | **[1,0] ✅** | **[1] ❌（300s 超时）** |
| `multi_pipe_8bit` | [] ❌ | [] ❌ |

### 判读

**唯一差异是 `div_16bit`，而这道题本身不确定**：同一 runtime（`3814e1df`）下，早前 42/88 那次跑出 `[1,1]`（失败），这次跑出 `[1,0]`（成功）。

- **因此 n=5 不足以判定 Y 更差**；但改动必须自证收益，**它没有显示出收益**。
- **结论：不采纳该提示。** 保留 X 配置的 `xelab` 检查思路，见下节。

### 附带发现：修复路径会放大非确定性

无修复时（官方 156 题重复跑）级别翻转 **0/312**；有修复时同题出现不同结局。
推测：修复依赖第二次生成，token 层的小差异会被放大成不同的修复结果。

**这解释了为什么"同配置重复"在同一题集上零翻转、却在修复路径上不稳。**

## 2. 更好的方案：零成本文本检查取代 `xelab`

### 动机

`xelab` 检测"实例化了未定义子模块"要 **1.12 秒/题**，而代价项按墙钟计量，秒级成本有真实分数含义。**如果同一判断用文本分析就能做到，成本近乎为零。**

### 第一版失败（必须记下）

只匹配 `Name inst (` → 在 VerilogEval 误报 **69/156**（`xelab` 真值 1），在 RTLLM 误报 **38/44**（真值 5）。
原因：`for (i = 0; ...)` 里的循环变量被当成了模块名。

**幸好拿 `xelab` 实测结果做了对照**，否则会推荐一个 44% 误报率的检查。

### 修正后的判别依据

**真实例化几乎总写成具名端口映射 `.port(signal)`；循环与条件语句不会。** 据此收紧后：

| 题集 | 文件 | 报缺失 | 该错误类真值 | **误报** |
|---|---:|---:|---:|---:|
| VerilogEval | 156 | 0 | 0 | **0** |
| RTLLM | 44 | **4** | 4 | **0** |

抓到的正是 `adder_16bit`(`adder_8bit`)、`adder_32bit`(`cla_16bit`)、`barrel_shifter`(`mux2X1`)、`div_16bit`(`div_16bit`)。

**覆盖该类错误 4/4，200 个文件零误报。**

未命中的两个真值属于**别的错误类**，本就不该被这个检查抓到：
- VerilogEval `Prob156`：`VRFC 10-3818`（变量被非法组合驱动）
- RTLLM `multi_pipe_8bit`：`TopModule` 本身未定义

### 与 `xelab` 的成本对比

| | 触发条件 | 成本 |
|---|---|---|
| `xelab` | **每题都跑** | 1.12 秒/题，无论有无问题 |
| 文本检查 | 只在真有缺失子模块时 | **0 秒**；触发时付一次修复生成（约 15 秒） |

**VerilogEval 156 题上文本检查触发 0 次 → 成本 0。** 这是它优于 `xelab` 的关键。

### 实现与验证

- 实现在 `04_project/amd_rtl_agent/submission/agent/runtime.py`：新增 `undefined_submodules()` 与 `check_submodules` 轨迹事件，插在源码结构检查之后、`xvlog` 之前
- 本地语法通过；**68 个测试全部通过**
- 把新 runtime 的函数拿到实例上对同样 200 个文件复跑，结果与独立脚本一致（0/156、4/44）
- **生效 runtime 未改动**（验证时仍为 `82e3a72e006e35d6`）；新版本为候选，哈希 `1b7d0cad1758338c`

## 3. 上机验证：**产生了实际收益**

### 做法

文本检查在 VerilogEval 156 题上触发 **0 次**，跑全量只会复现基线（可预测、信息量低）。
它真正触发的只有 4 道层次化题，而这 4 道在旧 runtime 下**必然 L0**。

所以只跑这 4 道，用**官方判定器**拿真实 L0–L3：

- 临时题集：把 4 道题复制进独立目录（不动原题集）
- `official_eval.py --tasks <subset> --samples 1 --deadline 300`
- 先占 `slot.sh`，`finally` 还原 runtime 并释放

### 结果

```
agent     set=0.2500   levels={'L0': 3, 'L3': 1}   tool_errors=0
baseline  set=0.2500   levels={'L0': 3, 'L3': 1}   tool_errors=0

adder_16bit     [0]
adder_32bit     [0]
barrel_shifter  [3]   ← 从 L0 救回到 L3
div_16bit       [0]
```

### 判读

- **旧 runtime 下这 4 道 agent 全是 L0（题集得分 0.0000）**；现在 `barrel_shifter` 变 L3，**题集得分 0.0000 → 0.2500**
- `barrel_shifter` 正是 RTLLM 那 5 道回归题之一，**agent 由此追平 baseline**
- 另外 3 道 agent 与 baseline **同时为 L0**，说明它们对双方都难，不是本检查能解决的范围
- **代价：VerilogEval 上触发 0 次 = 0 秒**；触发时才付一次修复生成

### 结论

**检测正确**（4/4，200 文件零误报）**且结果改善**（+1 道题）**且有实测代价为零的主基准**。
**采纳。**

### 防御措施

该检查每道题都跑，万一异常会直接打死整道题——**收益只有 1 道题，不值得冒这个险**。
已用 `try/except` 包裹，语义为"任何失败都等同于未检出"，管线行为与改动前一致。
另加 8 个单元测试（含那条导致 69 次误报的 `for (i = 0; ...)` 回归用例），全套 76 个测试通过。
