# 完美预言机：功能反馈的天花板

- 日期：2026-10-03
- 执行：原会话 Agent（工程负责人）
- 目的：回答一个前置问题——**如果 agent 拥有完美的功能反馈，它能修好多少题？**
  这决定"功能自检"整条路值不值得走

## 做法

用**官方测试台当完美预言机**（只在离线实验里用，**绝不进提交包**——规则要求）：

1. 取基线跑里已有的 38 道 L1 解答
2. 用官方测试台跑一遍，抓完整仿真输出——这就是 agent 若拥有完美测试台会看到的反馈
3. 按 runtime 的修复格式喂给模型，生成**一次**修复（与 `RTL_REPAIRS=1` 一致）
4. 用**官方 judge** 判修复后的解答

拿到的反馈形如：

```
Hint: Output 'out' has 59 mismatches. First mismatch occurred at time 30.
Hint: Total mismatched samples is 59 out of 219 samples
Mismatches: 59 in 219 samples
```

脚本 `oracle_v2.py`，占槽包装 `run_oracle.sh`（`trap` 保证释放）。温度 0，其余参数与基线一致。

## 结果

```
可判定题数 : 38 / 38
等级提升   : 10        （L1 -> L3）
达 L3      : 10
系数合计   : 7.60 -> 15.40
题集得分增量（分母 156）: +0.0500
```

明细：10 道升到 L3，1 道降到 L0（`Prob139_2013_q2bfsm`），其余 27 道仍是 L1。

升到 L3 的：`Prob083_mt2015_q4b`、`Prob086_lfsr5`、`Prob115_shift18`、`Prob117_circuit9`、
`Prob135_m2014_q6b`、`Prob150_review2015_fsmonehot`、`Prob152_lemmings3` 等。

**回收率 10/38 = 26%。**

## 换算成分数（满分线占位 2.5）

| 项 | 变化 |
|---|---|
| 题集得分 | 0.7603 → 0.8103 |
| 能力分 | **+1.50** |
| 增益 | 1.1274 → 1.2015 |
| 增益分 | **+2.78** |
| **合计收益** | **+4.28** |
| 成本：每题多一次测试台生成（约 13 秒） | 代价 19.75→32.75 秒，比值 0.840→0.506，代价 8.40→5.06 = **−3.34** |
| **净（完美反馈）** | **+0.94** |

## 关键：盈亏平衡点

真实的自写测试台**不是**完美预言机。探针实测可用率 **62.5%**（不是 100%）。按比例折算：

```
收益 +4.28 × 0.625 = +2.68
成本            −3.34
净              −0.66   ← 由正转负
```

**盈亏平衡的可用率 = 3.34 / 4.28 = 78%。**

## 结论

1. **天花板是高的**（+4.28 收益），**所以这条方向值得投入**——不是"连完美反馈都救不动"。
2. **但当前 62.5% 的可用率不够**，净收益为负。**必须先把可用率推到 78% 以上**才有正收益。
3. 探针里 3 道失败**全是编译错误**（`S11_next` 未声明、`expected_anyedge` 未声明、unexpected EOF 截断）——
   **这是"编译检查 + 重试"就能修的类别**，与我们在 agent 侧已经做过的事同类。
4. 成本侧的 3.34 分建立在"代价分母＝我们实测的 baseline 时长"这一假设上。
   **官方基准时长是赛前公布的固定值，尚未公布**；若它更宽松，成本会更小甚至归零。

## 尚未做

1. **实测自写测试台的真实端到端收益**——本实验只测了上限，没有测"模型自己写的测试台"能拿到多少。
   这是下一步，且必须以**可用率**和**净收益**两个数一起报。
2. **提高可用率的具体手段**未验证：测试台编译失败就重试、放宽 token 上限、要求逐信号打印。
3. 成本侧需要实测：一次测试台生成到底多少秒（本轮按 13 秒估）。
