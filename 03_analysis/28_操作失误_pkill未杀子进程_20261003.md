# 操作失误：`pkill` 脚本没有杀掉它的子进程

- 日期：2026-10-03
- 性质：**我自己的操作失误**，已清理并记录
- 一句话：**杀掉一个包装脚本，不会杀掉它启动的子进程**

---

## 发生了什么

我发现磁盘上已有现成的全 156 题参考自检
（`amd156_20261001T075230Z/reference156`），不需要重跑，于是执行：

```bash
pkill -f refcheck.sh
```

**bash 脚本确实被杀了，但脚本里的 `python3 - <<'PYEOF'` heredoc 成了孤儿进程**
（PPID 变成 1）**继续运行**，并持续 spawn `judge.py` → Vivado 综合任务。

**几分钟后我核对现场时才发现**：

```
残留进程数: 0 之前
  孤儿 PID=2242101  PPID=1  args=python3 -
  judge PID=2245790  PPID=2242101
  vivado / parallel_synth_helper ...
```

**即：我以为已经停掉的重跑，实际上还在占用 CPU 跑 Vivado。**

## 为什么危险

1. **资源浪费**：我在不知情的情况下持续占用机器，可能拖慢**队友的评测**（他也在用 Vivado）
2. **数据污染风险**：孤儿进程在继续往结果目录写文件，可能被误当成完整结果使用
3. **时序干扰**：如果当时有评测在跑，Vivado 争用会拉长它的墙钟，**影响代价项的测量**

## 正确处理

```bash
# 1) 杀掉整个进程组，而不只是脚本
kill -TERM -- -$(ps -o pgid= -p <script_pid> | tr -d ' ')

# 2) 或显式清理子进程
pkill -TERM -P <pid>
kill -TERM <pid>

# 3) 兜底：按实际工具名清理
pkill -9 -f "veval-judge"
pkill -9 -f "judge.py"

# 4) 【必须】核对残留
ps -eo pid,args | grep -E "judge.py|vivado|xsim" | grep -v grep
```

**第 4 步是这次发现问题的地方。没有它，我会一直以为已经停掉了。**

## 已做的补救

1. **两轮清理**，确认残留进程数 **0**
2. 我的不完整结果目录加了 `INCOMPLETE.md`，并把 8 个半成品移入 `_abandoned/`，
   **防止被误用为完整结论**
3. 核对**队友近 10 分钟无新文件**，确认没有影响到他正在跑的东西

## 教训

**此前几次操作失误的共同点**：我依赖了一个"看起来应该生效"的机制，而没有核对结果。

- 用 `git checkout` 还原不在 git 管理下的文件 → 静默失败
- 用 `/health` 判断服务是否重启 → 旧进程还在响应
- 用 `pkill -f 脚本` 停任务 → 子进程变孤儿继续跑

**三次都是同一个模式：验证的是"我以为的机制"，而不是"实际的结果"。**

**对应的纪律**：**任何"停止/还原/切换"操作之后，必须直接核对最终状态**——
进程没了、哈希对了、端口空了，而不是假设命令生效了。
