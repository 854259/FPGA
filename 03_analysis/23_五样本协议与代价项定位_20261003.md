# 战略判断：5 样本协议下的温度选择，与代价项的正确定位

- 日期：2026-10-03
- 执行：原会话 Agent（工程负责人）
- 性质：**不需要模型槽的分析**（全量配对正在占用单槽）

## 一、5 样本协议：我们该不该改温度

### 规则要求

- 官方要求 **5 样本协议**（156 题 × 2 模式 × 5 = 1560 次顶层运行）
- **计分用 pass@1**；`pass@5` 用于验证随机性，不参与计分
- 单题墙钟以赛事方发出请求到收到响应为准

### 我们的现状

`RTL_TEMPERATURE=0`，贪心解码。

**实测的重复性**（同配置两轮全量，312 个样本）：

```
级别翻转 0 / 312        系数合计完全相同
token 序列：agent 133/146 题完全相同，13 题 token 数不同
```

**即：温度 0 下并非逐位确定**（GPU 浮点归约顺序导致），但**差异没有传导到任何一道题的级别**。

### 三种选择的推演

| 方案 | pass@1 的形态 | 风险 |
|---|---|---|
| **A. 保持 T=0**（现状） | 5 次采样几乎相同 → pass@1 ≈ 我们的确定性得分 | 确定性失败仍失败 |
| B. 提高温度（如 T=0.7） | pass@1 = 5 次随机采样的均值 | 现在稳过的题可能随机翻车 |
| C. 微调温度（如 T=0.2） | 介于两者之间 | 收益不明，需实测 |

### 判断：**保持 T=0**

理由：

1. **计分用 pass@1，不是 pass@5。** 提高温度只有在"某题我们确定做错、但随机采样有时能做对"时才赚；
   而代价是"现在稳过的题随机翻车"。以我们 0.76 的水平，**稳过的题远多于稳错的题**，赌注是负期望。
2. **T=0 的 pass@1 是可复现的**。赛前我们可以精确知道会拿多少分，这对冲国一的策略价值很高。
3. **天然非确定性已经存在**（13/146 题 token 不同），但没有影响级别——**这正好是我们想要的形态**：
   有微小多样性，但不损失确定性收益。

### 但有一条必须核实的假设

**我不知道官方 5 样本如何汇总成 pass@1**（取第一次？取均值？）。若是取均值，T=0 等于我们现在的分数；
若是取第一次，也一样。**两种情况下 T=0 都不吃亏。**

**待办**：在 5 样本协议真正执行时，用实测确认"5 次采样级别是否一致"。
若发现不一致，再重新评估是否需要降低温度带来的收益损失。

### 尚未做

**5 样本协议本身没有跑过**（1560 次顶层运行，按当前 2 分钟/样本约需 52 小时）。
单样本结果**不得**表述为已完成 5 样本协议。

## 二、代价项：用正确的硬件事实重做判断

### 更正后的硬件事实

上一份记录说"没有 GPU、跑在 CPU 上"——**已更正**。实际：

```
AMD GPU（ROCm/HIP），DID 0x744b，PwrCap 241W
llama-server 链接 libggml-hip / libhipblas / librocblas / libamdhip64
进程持有 /dev/kfd 与 /dev/dri/renderD133
推理时 GPU use = 100%
吞吐 29.65 tok/s（900 tokens / 30.3 s）
VRAM 39%（约 18.7 GB ≈ 模型大小 → 全部层都在 GPU 上）
```

### 正确的带宽账

- 19.1 GB 权重 / token × 29.65 tok/s = **566 GB/s**
- 该档位显卡理论带宽约 **864 GB/s**
- **达到约 65%，GPU 已 100% 占用**

### 判断

**生成速度由权重矩阵乘主导，属显存带宽受限。** GPU 已打满，**配置层面没有找到杠杆**：

| 候选 | 为什么帮助有限 |
|---|---|
| `-t`（CPU 线程） | 已实测 8/32/64/128 无差异——GPU 在算 |
| `-b` / `-ub`（批大小） | 影响 **prompt 处理**，不影响逐 token 生成 |
| `-fa`（flash attention） | 影响注意力部分；16K 上下文、短序列下占比小 |
| 重编译（AVX-512 等） | 与 GPU 路径无关 |

**65% 的带宽利用率对 llama.cpp 属正常水平**，要再往上需要上游 kernel 层面的工作，不是配置能解决的。

### 真正的杠杆只有两个，且都改模型本身

1. **更激进的量化**（如 Q3_K_M，约 13 GB → 理论吞吐 +45%）
2. **更小的模型**

**两者都改变模型，属于用户决策，我不擅自改。**

### 结论的准确表述

- ✅ **能说**：当前模型+量化+llama.cpp/ROCm 下，配置层面没有找到提高吞吐的杠杆；GPU 已 100% 占用。
- ❌ **不能说**：代价项"不可能"改善。换量化或换模型都能改善，只是那是**模型选择**问题，不是配置问题。
- ⚠️ **未做**：GPU 侧调优（批大小、显存频率、不同 ROCm 版本）没有实测，所以不下"已到极限"的断言。

**这与上一份记录的区别**：上一份说"被 CPU 内存带宽锁死、方向关闭"（错误）；这一份说"当前配置下无杠杆，真正的杠杆在模型选择上"（有据）。
