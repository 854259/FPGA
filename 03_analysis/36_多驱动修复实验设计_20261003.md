# 多驱动修复实验设计（固定修复预算）

> ## ⚠️ 已推迟：测试集选错，且未先算价值
>
> **本设计的测试集是 H3 变体的四道失败候选，而那四道的 7 规则版本（稳定版）全部能正常展开。**
> 因此它测的是「能不能修好一个已被否的变体的错误」，**结果不改变任何决定**。
>
> **正确顺序应是**：先找到**稳定版**里能被检出的真实错误 → 再算「修好了值多少」 → 才谈修复实验。
> 而稳定版 156 道里只有 1 道能被 `xelab` 检出（`Prob156`），且**该题上限是 L1**；
> 经计算，这个检查在官方基准时长 < 21 秒时是净负（见 `37_xelab检查_有条件的否定_20261003.md`）。
>
> **配套脚本 `bench/multidriver_repair.py` 已删除**——留着它会让后来者跑出「4/4 修好了」这类
> 与稳定版无关的结论。若将来隐藏题集确有多驱动需求，再按上面的正确顺序重写。
>
> 以下为原始设计，保留作记录。

## 要回答的唯一问题

**把 `xelab` 的多驱动诊断交给模型，在固定修复预算内，它能不能修好？**

**不回答**：整体题集得分能提高多少（那需要全量对照）。

## 为什么值得做这个实验（而不是继续找规则）

| 已证 | 未证 |
|---|---|
| 多驱动**能被识别**：`xvlog` 通过而 `xelab` 失败，156 道里 1 道，**零误报**，增量 1.16s/题 | **能不能修好** |
| 诊断**只依赖候选代码**，正式运行时可得 | 修复会不会引入新退步 |
| 四道 H3 候选**确实**因多驱动失败（三组对照已证） | 修复后官方等级能否提升 |

**修复是这条链上唯一还没测的环节。**

## 测试集

**四道已确认多驱动失败的候选**（来自 H3 run 的提交代码）：

| 题 | 错误 | 官方等级（H3 run） |
|---|---|---|
| `Prob006_vectorr` | `VRFC 10-3823 'out' multiple concurrent drivers` | L0 |
| `Prob128_fsm_ps2` | `VRFC 10-3818 'done_reg' invalid combination` | L0 |
| `Prob133_2014_q3fsm` | `VRFC 10-3818 'z_reg' invalid combination` | L0 |
| `Prob137_fsm_serial` | `VRFC 10-3818 'done_reg' invalid combination` | L0 |

**为什么用这四道**：它们是**真实失败**，不是构造的；而且**已知失败原因**，所以"修好了没有"有确定的判据。

**⚠️ 边界**：这四道来自技能**变体**，不是稳定版。用它们**只回答"给定诊断能否修复"**，
**不能**把结果算成稳定版收益，**也不能**据此重新采纳 H3。

## 方法

对每一道，构造一次单轮修复请求：

```
输入 = 原题面
     + 失败的候选代码
     + xelab 的原始诊断（VRFC 10-3818 / 10-3823 行）
约束 = 固定修复预算 1 轮（与 RTL_REPAIRS=1 一致）
```

**然后**：
1. 用官方判定器判修复后的代码 → 记录 level
2. 单独再跑一次 `xelab` → 记录多驱动是否消失
3. 与修复前对比 → 记录是否退步

**固定项**：技能 `f4c4c8e2`、baseline `537783e3`、runtime 与对照组一致、
`RTL_TEMPERATURE=0`、`RTL_MAX_TOKENS=8192`、deadline 300。

## 四个必须同时报的量（评审要求）

| 量 | 怎么测 |
|---|---|
| **正确代码被误报多少** | 已在 156 道上测过：**0** |
| **错误代码能检出多少** | 稳定版 1 道；本实验集 4 道（已知） |
| **检出后实际修好多少** | 本实验的核心输出：`修复后 xelab 通过数 / 4` 与 `官方等级提升数 / 4` |
| **增加多少耗时** | xelab 增量 1.16s/题 + 修复轮次的模型耗时 |

## 明确的"不能做"

- **不允许直接删掉某一处赋值来"消除"多驱动**——哪一处符合题意需要判断。
  实验必须让模型自己决定保留哪个驱动。
- **不能只报 xelab 通过**：还要报官方等级，因为"展开通过"不等于"功能正确"。
- **不能把这四道的结果外推到隐藏题集**。

## 判据（先写死）

```
xelab 通过数 >= 1  且  无新增退步(level 不下降的题数 >= 修复前)
    -> 说明"给定诊断可以修复"，值得把 xelab 检查纳入流程
否则
    -> 说明只能识别、不能修复，检查的价值降到"仅用于拒绝"（避免提交必然失败的代码）
```

**注意**：即使修复率低，检查仍有价值——**在单题限时内提前发现必然 L0 的代码，
可以换一次生成，而不是白提交**。这一点要在结论里写清。

## 成本

4 道 × 1 轮修复 ≈ 4 次模型调用，**约 10–15 分钟**（含判定）。

## 执行前置

1. **模型槽空闲**（当前被 runtime 对照实验占用）
2. runtime 对照实验结束并已按预定标准处置（采纳或还原）
3. 不修改官方 baseline / 判定器 / 题集
