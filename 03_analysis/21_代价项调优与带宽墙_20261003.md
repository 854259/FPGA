# 代价项调优：线程数无关，撞的是内存带宽墙

- 日期：2026-10-03
- 执行：原会话 Agent（工程负责人）
- 结论：**代价项无法靠配置优化。模型跑在纯 CPU 上，已是内存带宽受限。**

---

## 1. 起因：一个看起来很大的机会

探查服务时发现：

```
CPU: AMD EPYC 9334 ×2  ->  64 物理核 / 128 线程
/dev/nvidia* : 不存在      libcuda : 不存在
启动参数: -ngl 99 -c 16384 -np 1 -t 8 --reasoning off
吞吐: 29.8 tok/s
```

**没有 GPU，模型跑在 CPU 上，而且只用 8 个线程。**

当时判断：代价 = `10 × min(基准时长/实测时长, 1)`，把实测时长压下去代价值直接上升。
若吞吐翻倍，预计 **代价 8.40 → 10.00（+1.60 分）**。

## 2. 实测：线程数完全不影响吞吐

| 线程数 | 吞吐（3 次） |
|---|---|
| `-t 8` | 29.2 / 29.3 tok/s |
| `-t 32` | 29.4 / 29.3 tok/s |
| `-t 64` | 29.3 / 29.3 tok/s |
| `-t 128` | 29.3 / 29.3 tok/s |

**8 到 128 线程，吞吐一模一样。**

服务端日志给出的权威数字也一致：
```
eval time = 23555.83 ms / 700 tokens ( 33.70 ms per token, 29.67 tokens per second )
```

## 3. 判读：内存带宽受限

- 模型文件 19.1 GB（Q4_K_M），每生成一个 token 要把全部权重读一遍
- 19.1 GB × 29.7 /s = **567 GB/s**
- 双路 EPYC 9334 的 24 通道 DDR5 理论带宽约 920 GB/s，实测约 60% 属合理区间
- **线程数无关，正是带宽受限的典型特征**——加线程不能增加带宽

**所以 `-t 8` 根本不是配置错误。我的假设是错的。**

## 4. 顺带排除：AVX-512

构建配置：
```
GGML_SYSTEM_ARCH: x86
Adding CPU backend variant ggml-cpu: -msse4.2;-mf16c;-mfma;-mbmi2;-mavx;-mavx2
```
**只启用了 AVX2，没有 AVX-512**，而该 CPU 有 `avx512f/avx512bw/avx512vnni`。

但既然已确认是带宽受限，**加 AVX-512 大概率也帮不上**（带宽不变，算得再快也没用）。
重新编译的收益/风险比不划算，**未做**。这里不下断言，只记录未验证。

## 5. 战略含义

**代价项被硬件锁死了。** 在当前模型与量化下：

- 吞吐 ≈ 29.7 tok/s，无法通过线程、批大小或构建选项改善
- 要更快只有两条路，**都改变模型本身**（属于另一个量级的实验，且会动到质量）：
  1. **更激进的量化**（如 Q3_K_M，约 13 GB → 理论吞吐 +45%）
  2. **更小的模型**
- 两条都与"模型选择已定"的前提冲突，**需用户决策，我不擅自改**

**因此：代价项的 +1.6 分不在可及范围内。** 我把这个方向关闭，并把理由留存。

## 6. 附带发现：`Prob147` 的失败原因

VerilogEval 7 道 agent L0 里，`Prob147_circuit10` 的轨迹是：

```
check_source rc=1
  "Return a complete TopModule ending in endmodule. Output reached the token limit; shorten the implementation."
```

`solution.v` 有 19173 字节，以 ` ```systemverilog ` 开头，**`endmodule` 出现 0 次**。

**即：模型在代码块里写了约 8192 token 的推理注释（用 `//` 分析波形），撞上 token 上限仍未写完模块；
第二次修复尝试又被 supervisor 按截止时间杀掉。**

输出里**没有可用的设计**，检查器的拒绝是正确的。

服务日志另有一条相关警告：
```
chat template supports preserving reasoning, it is enabled by default
(may use more tokens, disable via --no-reasoning-preserve)
```
**未验证**它是否与本例有关（启动参数已有 `--reasoning off`）。记录下来备查。

## 7. 方法论教训：两次测量都是无效的

**第一版调优脚本测出来的数据全都是假的。**

`stop_server` 之后没有等端口真正释放，`wait_ready` 又只看 `/health`——
**旧进程还在响应时就被判为"启动成功"**，请求全打到旧进程上。
`-t 8` 和 `-t 64` 的"成功"是假的，`-t 32`/`-t 48` 才是真失败（端口未释放）。

**第二版加了端口检查，但吞吐取值失败**（日志解析没抓到）。
**第三版改用客户端计时才拿到可信数据。**

**教训：验证一个进程是否真的重启，必须核对【新 PID + 命令行参数 + 端口归属】，不能只看服务是否响应。**
