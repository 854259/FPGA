# xelab 展开检查：稳定性、覆盖与成本实测

- 日期：2026-10-03
- 执行：工程负责人，**未调用模型**（纯 EDA）
- 数据：稳定版 `full156_declfix_20261003` 的全部 156 道 agent 提交代码
- 判据（评审要求）：**正确代码被误报多少 / 错误代码能检出多少 / 增加多少耗时**
  （"检出后实际修好多少"需要模型槽，本实验不回答）

---

## 1. 为什么做这个检查

复验四道新增 L0 时确认：失败**不在编译，而在展开**。

```
xvlog_dut      rc=0     ← agent 自检到这里就通过了
xvlog_fixture  rc=0
xelab          rc=1     ← 只有官方流程跑这一步
```

四道的展开错误：

| 题 | 错误 | 信号 |
|---|---|---|
| `Prob006_vectorr` | `VRFC 10-3823 variable 'out' might have multiple concurrent drivers` | `out` |
| `Prob128_fsm_ps2` | `VRFC 10-3818 'done_reg' is driven by invalid combination of procedural drivers` | `done_reg` |
| `Prob133_2014_q3fsm` | `VRFC 10-3818 'z_reg' ...` | `z_reg` |
| `Prob137_fsm_serial` | `VRFC 10-3818 'done_reg' ...` | `done_reg` |

**诊断信号可仅从候选代码取得，不依赖隐藏测试台**（评审已独立验证：只加载候选即报错；
按官方 L1 流程加载 tb+ref 报同样错；7 规则旧候选独立展开通过）。

**缺口**：`runtime.py` 只跑 `xvlog --sv`，通过即接受候选，**从不跑 `xelab`**。
代码注释里本来就知道这件事（"只有展开才暴露，而展开要花约一秒"），
但当时只用文本检查覆盖了"缺失子模块"一种情形。

## 2. 本实验方法

对稳定版全部 156 道：
1. `xvlog -sv --nolog dut.sv`（测量退出码与耗时）
2. 若通过，再 `xelab <top> -s snap --nolog -timescale 1ps/1ps`（测量退出码与耗时）
3. 与官方判定等级对照

**不加载参考解或测试台**——因为 agent 在正式运行时拿不到它们。

## 3. 结果

| 指标 | 值 |
|---|---|
| 题目数 | 156 |
| `xvlog` 就失败 | **4 道**（`Prob082_lfsr32`、`Prob134_2014_q3c`、`Prob144_conwaylife`、`Prob147_circuit10`） |
| **`xvlog` 通过但 `xelab` 失败** | **1 道**：`Prob156_review2015_fancytimer`（报多驱动） |
| **误报：官方 L3 中 `xelab` 失败** | **0 道** ✅ |

**按官方等级的分布：**

```
L0:  6 道  →  xvlog 失败 4、xelab 失败 1、两项都过 1
L1: 38 道  →  全部 xvlog 通过、xelab 通过
L3: 112 道 →  全部 xvlog 通过、xelab 通过
```

**耗时：**

| | 均值 | 合计 |
|---|---|---|
| `xvlog` | 1.07s | 167s |
| `xelab` | **1.16s**（中位 1.13s，max 4.03s） | 176s |
| 两者合计 | 2.2s/题 | 343s |

**→ 由于我们已经跑 `xvlog`，这个检查的增量成本是 1.16 秒/题。**

## 4. 能说与不能说

**✅ 能说**
- 在稳定版 156 道上，**`xvlog` 通过而 `xelab` 失败的有且仅有 1 道**，且报的是多驱动。
- **这个检查在 156 道上零误报**：所有 150 道官方判为 L1/L3 的题，`xelab` 全部通过。
- 增量成本 **1.16 秒/题**（合计约 3 分钟/156 题）。
- 检查**只依赖候选代码**，正式运行时可得。

**❌ 不能说**
- **不能说这能提多少分**。稳定版只命中 1 道；若修复后达到 L1，则 `+0.2` 系数 → `+0.00128` 题集得分，
  **而且要扣掉时间变长对代价项的影响**（未算）。
  **⚠️ L1 只是区间下界、不是预期值**——修复后能达到 L2/L3 时收益更高（+0.00449 / +0.00641 题集得分）。
  **收益的实际值未测定；把这个检查值不值得加算清楚的是
  `37_xelab检查_有条件的否定_20261003.md`（结论：官方基准时长低于约 20.6 秒时净负）。**
- **不能说这道一定修得好**：检出 ≠ 修好，需要模型槽做单变量实验。
- **不能说"多驱动"是这 4 道 H3 L0 的全部原因之外还有别的**：四道都报了同类错误，
  但评审指出**不能自动删掉某处赋值来"消除"多驱动**——编译通过之后仍可能有功能错误。

## 5. 一个必须写在明面上的边界

**`Prob156_review2015_fancytimer` 正是官方参考解自检也未达 L3 的 4 道之一**
（参考解自检给了它 L1）。

- 这只说明该参考实现本次自检为 L1，**不能推出任何实现的上限都是 L1**。
- 若修复只达到 L1，则相对 L0 增加 `0.2` 系数；修复后实际能达到的等级尚未测定。
- **不能提前承诺拿到 L3，也不能把参考解成绩当成所有方案的上限。**

## 6. 与 H3 的关系

**四道 H3 新增 L0 的 7 规则旧候选全部展开通过**（评审已独立验证）。

因此：
- **不能把"检出了 H3 的四个错误"算成稳定版的收益**；
- **更不能据此重新采纳 H3**——H3 的 agent 得分是下降的，按预定标准不采纳。
