## 先核查已有能力，避免重复实现

旧开发版已经有声明修复、重复检测、诊断压缩和候选回退等工作，当前官方适配版不能假定全部继承。先对比旧 `agent.py`、当前 `submission/runtime.py` 与服务器运行源码快照，列出“已有且验证 / 需要迁移 / 新增候选”。

迁移必须尊重官方输入边界：只能用题面、候选源码及智能体自己的检查；不得把旧开发评测可见的参考测试反馈接入当前智能体。不要整包覆盖新版本。

## 建议顺序与具体做法

### 1. 接口与源码预检

- 从题面提取模块名、端口名、方向、位宽。RTL 的 interface 字段可能为空，不能依赖单独接口文件。
- 检查模型输出提取、完整模块、声明与明显格式问题。不能仅凭出现 endmodule 判定源码完整。
- 复杂参数、宏和难以可靠解析的接口应标为无法自动确认，交给真实编译诊断，不凭正则猜测后强改。
- 使用现有能力优先，记录误报和漏报；自动变换不能改变设计逻辑或变成按题号拼答案。

### 2. 分类修复与较好候选保留

| 类型 | 建议反馈或动作 |
|---|---|
| 接口/声明 | 指出具体名称、方向、位宽或声明位置 |
| 语法/编译 | 关键报错与附近源码，避免混入无关日志 |
| 自测功能失败 | 可复现输入序列、由题意推导的预期结果与实际结果 |
| 重复返回 | 检测代码哈希是否变化，避免无意义重复检查或请求 |
| 修复变差 | 保留此前完整、通过更多可靠内部检查的候选 |

“较好”只按智能体有权获取的内部证据排序，不使用外部 L1/L2/L3 或参考测试结果选择候选。内部编译通过也不能宣称正式 L1/L3。优先保留可用候选，避免最后一次不完整输出覆盖它。

先保持同样模型调用/修复上限比较；不因多调用一次而直接宣称策略本身有效。

### 3. 针对题意的功能自检（先做小范围试验）

对 19 道 L1 先分类，再挑有代表性的简单题验证自测方法，不直接为全部题引入昂贵的通用测试生成器。

- 计数器：复位值、使能保持、最大值回绕、正确时钟沿。
- 状态机：关键输入序列、状态转换、重叠序列、复位后行为。
- 移位寄存器/边沿检测：位序、时序延迟和边界条件。
- 仅使用题面明示的语义；题意未规定的初值或行为不擅自添加断言。

测试台也会错：独立检查语法、驱动时序、采样时刻和预期值。自测失败时先区分候选错误、测试台错误与题意歧义，不盲目让模型迎合错误测试。不要利用参考答案来构造智能体的测试台；外部参考评测只用于最终衡量效果。

自测通过只覆盖有限激励，不是形式证明，也不保证通过官方测试。计入测试生成的模型调用、编译、仿真与修复总耗时。

### 4. 按需加载 skill

保持简短通用输出约束。根据题面与实际诊断加载声明、状态机、时序等小型清单，避免每次塞入全部规则。触发条件不能依赖题号或参考答案；记录 skill 内容和哈希。

这是候选策略：提示更短或规则更多都不自动代表更好，要检查成功题退化和实际通过率。

### 5. 耗时与部署

分开统计模型生成、内部检查、外部判定、排队和请求准备时间。先定位慢点再优化，不把外部评测器加速误报成智能体解题加速。

并行或缓存需要确认隔离、许可与显存条件；不得跨题缓存答案。模型/量化/推理服务改变后重新跑匹配 baseline。AMD ROCm 兼容性单独尽早验证，NVIDIA 结果不能替代。

## 实验与交付要求

1. 先提交当前官方版能力清单，确定哪些优化是迁移、哪些是新增。
2. 每次只改一个主要因素，固定模型、数据、调用上限和时间预算；若预算改变，所有对照组保持一致并单列实验。
3. 小集同时包含目标失败类型与原已通过控制题，排除已知参考异常对收益判断的干扰；不挑完有利结果后再定义题集。
4. 报告完整代码比例、L3、改善/退化、重复修复、请求数、超时和耗时。不能只报告修复成功案例。
5. 局部改善后再新目录全量验证，保留配置、代码和 skill 哈希。此前原始成绩不覆盖、不拼接。

希望队友返回：能力核查表、一个优先改动的实现与验证、逐题对照、失败分析、是否值得扩大测试的结论。本交接没有启动新模型实验，也不声称这些改动已提高通过率。
